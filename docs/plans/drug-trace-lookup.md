# 扫药品追溯码录入：调研与接续计划

> 状态：仅计划与公开文档调研，未正式接入。当前阻塞是账号身份验证与接入资格，不是扫码算法。
> 按用户要求保存在 `feature/drug-trace-lookup-plan`；分支名称不代表已授权产品开发、PR、合并或发布。

## 1. 目标与本次范围

减少家庭药箱录入药名、规格、厂家、批号和有效期的抄写工作。优先验证「本地扫追溯码 → 正式接口查询 → 用户核对 → 保存」是否可行；保留现有 OCR 和手动录入作为兜底。

本次只记录结论、资格问题、后续验证和换电脑接续方法。不修改应用、依赖、数据库或隐私说明，不部署后端，不创建 APK、版本号或 Release。不将本计划或后续 PoC 自动合并到 main。

## 2. 已核实的公开资料

### 2.1 不要求把药箱改为支付宝小程序

- 支付宝「扫一扫」扫描受支持的药品追溯码，可以进入阿里健康「码上放心」展示信息，见来源 1。
- 独立 Android App 可以自行读码，再通过获准的数据接口查询；用户不必因采用该架构而安装支付宝或淘宝。
- 支付宝小程序 `my.scan` 只返回码内容、码类型等，不返回药品资料。没有核实到可把「码上放心」小程序的完整查询结果直接回传给本 App 的公开能力，见来源 2。
- 不抓包复用内部接口、不模拟消费者登录、不绕过平台权限。

### 2.2 商品条码和追溯码不能混用

| 类型 | 常见含义 | 录入边界 |
| --- | --- | --- |
| 商品条码，例如 EAN-13 | 同一药品包装规格可共用 | 查库后可能得到基础资料，不能据此确定某盒的批号或有效期 |
| 药品追溯码 | 对应具体包装单元，区分包装层级 | 正式平台可能返回该包装的生产及有效期信息，仍须核对 |

码上放心本次核对的接口描述以「8 开头、20 位数字」为过滤规则；这不是所有追溯体系的统一规则。其他编码或二维码不能仅凭外观认定无效，也不能自动打开其中的任意 URL。

官方说明商品条码维护不全、也不一定准确，不能保证追溯码与商品条码的准确映射。不承诺所有药盒、所有追溯平台都能查询到，见来源 3。

### 2.3 存在正式的根据码查询接口

淘宝开放平台接口，见来源 4：

```text
alibaba.alihealth.drugtrace.top.lsyd.query.codedetail
```

- 业务入参包含企业标识 `ref_ent_id` 和追溯码列表 `codes`；公共参数包含 AppKey、时间戳及签名等。
- 文档列出药品名称、批准文号、剂型、制剂规格、包装规格、企业信息、包装层级、生产日期、批号和有效期至等返回字段。
- 接口存在不等于本项目已获使用权限；返回结构可能有多条生产信息，不能默认取第一条。
- 文档中 `exprie` 是类似「12月」的有效期时长，`expire_date` 等字段才涉及具体有效期至；实施时重新核对各日期字段语义，不能把时长当日期，也不从生产日期擅自推算到期日。
- 企业对象不一概等于生产厂家，需核对角色；不承诺该接口提供完整说明书、品牌或适应症等全部字段。

### 2.4 资格和收费尚未确认

公开流程涉及码上放心入驻、签约、开放平台开发者认证、应用审核、权限包及企业绑定。主要面向医药企业、医疗机构和软件服务商，见来源 3、5。

「免费 API／不需用户授权」标签不等于匿名开放、不需开发者资格、不需企业绑定，也不证明平台全部服务免费。个人家庭药箱用途能否获准，尚未得到平台确认；不能虚构企业、套用其他主体资质或把已有营业执照视为全部授权。

## 4. 换电脑接续

### 4.1 先同步计划分支

本地 commit 不会自动出现在另一台电脑。须先由用户明确允许共享，再推送本计划分支；不顺带创建 PR、合并或触发发布。此步骤不应被误报为已经完成，实际推送状态以交接回复和远端为准。

远端分支已存在后，在新电脑的主 workspace 检查工作区及 worktree，再执行：

```bash
git fetch origin
git worktree add .worktrees/drug-trace-lookup-plan -b feature/drug-trace-lookup-plan origin/feature/drug-trace-lookup-plan
```

若同名本地分支或目录已存在，先检查并使用正确的既有 worktree；不覆盖、不强制重置、不嵌套创建 `.worktrees/`。

### 4.2 在新电脑重新登录

1. 使用新电脑已配置的 Edge 专用浏览器及官方本地 Playwright MCP；首次烟雾检查只访问 `about:blank`。
2. 需要用户操作时，先确认确实有可见窗口。无窗口模式不能让用户在桌面中操作；若工具不支持直接切换，明确报告并按本机受支持的配置处理，不假称已显示登录页、不关闭其他任务的浏览器。
3. 打开官方入口 <https://open.taobao.com/> 或 <https://work.open.taobao.com/>。登录、扫码、短信、MFA、实名或风控验证由用户自行完成，agent 停在该处。
4. 仅用页面 pathname、标题或可见账号名确认登录，不输出认证回调地址或认证请求头。
5. 不从旧电脑读取、复制、导出或迁移浏览器配置、Cookie、存储状态、密码、验证码、Token 或其他凭据；不复用旧电脑的 Dev Tunnel，不为此开放网络访问。
6. 若进入实名资料、企业主体、协议签约、付费或接口权限申请页面，先说明所需内容并取得用户对具体操作的确认。此前的注册请求不等于可代填主体、接受条款、付费或申请全部业务权限。

## 5. 先做资格与数据可用性判断

以下是需要向平台核实的问题，不是已向平台提交的申请：

- 非商业家庭药箱、个人开发者是否可接入？若需企业／ISV主体，其要求和本次可用授权是什么？

**Go 条件：** 用途、主体、费用和数据使用范围得到确认，用户接受必要成本和后端方案，并明确允许开始 PoC。

**No-go 条件：** 资格不符、用途不允许、条款不相容或费用不接受。停止该路径，向用户汇报；不以未公开接口、其他企业账号或解除安全限制代替正式授权。

## 6. 获准后的小范围 PoC（尚未实施）

从届时最新 `origin/main` 另建 `.worktrees/drug-trace-lookup-poc/` 和 `poc/` 分支，默认仅本地验证。先确认样本、验收条件和真实服务调用授权，再开始。

### 候选架构

```text
Android 本地读码
    → 用户明确允许发送本次码值
    → 受控后端保存供应商密钥、签名、限流及最小化日志
    → 获准的正式查询接口
    → 带来源和缺失提示的候选资料
    → 用户核对后显式采用
```

- 不将供应商共享密钥写入 APK、Git、PR、日志或聊天；如何安全配置凭据单独确定。
- 只发送查询所需的本次码值等必要数据，不上传整个药箱、照片或用户身份；不默认将完整追溯码写入日志。
- 可先评估 ML Kit 随包条码模型，支持本地 Code 128、EAN-13、二维码等解码；它与现有文字 OCR 是不同依赖。新增前核对许可、供应商条款及随包通知，不因本地处理而宣称 SDK 无通信，见来源 6。
- 不承诺无需后端即可安全使用企业签名接口；不在本计划阶段部署后端。

### 最小交互与核心规则

1. 添加页扫码；同时发现商品码和追溯码时，让用户明确选择，不误扫后静默查询。
2. 识别受支持的码并在请求前说明联网及发送范围；查不到、取消、断网或拒绝权限都能继续 OCR／手动录入。
3. 展示名称、规格、企业角色、批号、生产日期、有效期及来源；缺失留空，冲突或多个结果要求用户核对。
4. 仅显式采用，不覆盖人工填写；包装数量不等于当前余量。同商品不同盒不自动合并批号和日期，同一追溯码重复扫描提示可能重复录入。
5. 不用扫码次数判断真假，不将「查询到信息」当作真伪鉴定，不自动生成或导入剂量、禁忌等说明书安全内容。
6. 取消页面后迟到响应不回写新草稿；重试、重复扫码不重复保存记录。

### 验证与产出

- 在用户同意的少量实物包装中覆盖不同药品／厂家、同药不同批次、缺失字段、不同包装层级和查不到的码；不公开真实完整追溯码或个人药箱资料。
- 分别记录「离线解码」「真实接口查询」「字段与包装核对」是否成功，不把合成响应、UT 或扫码成功等同于真实数据可用。
- 只添加必要规则 UT；按实际逻辑风险构建、Lint，并按仓库 skill 在来源可核实的专用 AVD 验证取消、失败和采用流程。普通手机不在常设测试授权内。
- 报告命中情况、字段完整性、实际延迟、费用和未验证项；真实服务或真实包装未验证时明确标注。实验 APK 不进入正式更新通道。
